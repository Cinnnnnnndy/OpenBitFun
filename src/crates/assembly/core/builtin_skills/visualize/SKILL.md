# Visual answers in FlowChat

For a visual explanation, publish the figure in this turn. For an independently openable webpage, implement it in the workspace and link the entry file. A request for a working object, such as a pendulum, is enough to publish an inline simulation. Use a simple Markdown table or Mermaid diagram when the requested information fits those formats.

Use Write with a single patch section. The first line names the session artifact. Put the literal HTML fragment below it. Replace the slug with a short ASCII name.

    +++ openbitfun://current-session/artifacts/visualizations/v2/map-cities.html
    <h2>Great Lakes cities</h2>
    <script type="application/json" data-visual-atlas="1">{"places":[{"name":"Chicago","country":"US"},{"name":"Toronto","country":"CA"}]}</script>

For geographic maps use a map-<slug>.html destination so the background check expects a basemap. For cities across a region use the declaration above with the requested places. The built-in atlas provides real coasts, lakes, rivers, administrative boundaries, projections and place labels offline. Each place accepts a name, optional ISO country code and region, or sourced coordinates in [longitude, latitude] order. Optional bounds use [west, south, east, north]. Set language for translated labels if needed. Report ambiguous names or ask for detail when the supplied names do not uniquely identify places.

For an itinerary between real sights, streets, or stops within a city, put the stops on a street basemap. This also applies when visualizing an itinerary from an earlier message. Use one atlas declaration with `detail: "street"`, `city`, optional ISO country code and the public names of the stops in visit order. For example:

    <script type="application/json" data-visual-atlas="1">{"detail":"street","city":"Paris","country":"FR","places":[{"name":"Tour Eiffel","osmTag":"man_made:tower"},{"name":"Arc de Triomphe","osmTag":"building:triumphal_arch"}]}</script>

FlowChat looks up named public stops in the city and saves their resolved coordinates and the verified street basemap for offline replay. Submit each public name directly. Keep descriptions such as “evening walk” or “historic section” in the display label; use the short local place name as the query. Only supply WGS84 coordinates [longitude, latitude] when they come from an identified source. For disambiguation a stop accepts a public search name in `query`, an OSM classification in `osmTag`, or an `osmId` from the reported candidates. For a rail station use the local station name with `railway:station`. For a specifically requested pedestrian street use its street name with `highway:pedestrian`. Select an ID only if both its classification and its location match the itinerary. Use an entrance or street segment that fits the itinerary and identify it in the label. On a failed lookup, use the reported candidates to repair the same map. A mismatched tag can be dropped. If the intended place is still unclear, ask for clarification. Keep each requested stop on the map, including when revising an earlier itinerary. A stop's marker has `data-map-stop` equal to its zero-based index for itinerary controls. Markers indicate stops; draw a navigation path only with sourced route geometry. Never invent a shoreline, a road, or a distance scale. For an explicitly offline or private location, use locally supplied, sourced geometry. Figures with bound data must supply coordinates or local geometry for their stops. Mark a custom projected SVG with `data-visual-map`, `data-map-source="https://…"`, and `data-visual-region` on its projected basemap geometry. If street data is unavailable, explain this visibly and return a stop list (`<ol data-visual-itinerary>`) without a geographic drawing or scale on the same URI.

For architectural diagrams and mockups, use readable HTML and SVG. Label responsibilities, relationships and direction. Provide a working selection or input when it explains something. Use native buttons and inputs, explicit axis labels and units, responsive dimensions and theme variables such as --foreground, --background, --muted-foreground and --viz-series-1. Tabs with role="tab" select panels by aria-controls. For charts the frame supplies Apache ECharts when the fragment uses echarts.init(). Give the chart a nonzero height and resize it with its container. For a simulation implement the moving object and mark it with data-visual-motion so the host can check it. Respect reduced motion and keep essential labels visible.

Write and Edit check the fragment in the background. For a map the host resolves the atlas declaration and checks the resulting geometry. Read the tool result and repair reported errors with Edit on the same URI. Skip temporary scripts, local servers and browser previews. Finish with a short reader-facing reply. FlowChat attaches the checked figure automatically. To position multiple figures in a particular order, copy each exact reference onto its own line.

Add "mode":"wide" to the reference for a wide figure. Use window.openai.setWidgetState({modelContent, privateContent}) for selections that survive replay. Keep reader-only selections in privateContent. To expose a design adjustment in the figure menu, create new Tweak({container, onChange}) and register a slider, toggle, color or selection with addSlider, addToggle, addColorPicker or addSelect. Live binding updates are available through window.openai.visualization.onData(name, callback). For a locally imported reference kit, authoring/SKILL.md contains its extended component API.
